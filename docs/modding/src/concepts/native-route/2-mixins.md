# Mixins: `[[native.mixin]]`

A mixin changes one game function. You name the function and the place in it (its start, its return value,
one call inside it, or its whole body), and write your code there as a small Rust function, the **helper**.

Use a [hook](../hooks-and-the-host.md) or [Part method](../parts.md) when it exposes what you need.
Use a mixin when you need to patch the game function itself.

## Example

This mixin runs at the start of `on_tick_rate_changed`, the follow-up to a server rate write or the
end of a sprint. It reads the private `CommonGame::clock` field through `ServerGame` and skips the
follow-up at a chosen tick rate. The rate has already been written; this does not veto the write.

Add this row to the `sunrise-mod.toml` of your native mod. Keep the `[native]` pins generated by
`cargo sunrise-mod new`.

```toml
[[native.mixin]]
id = "head"
target = "sunrise_gameplay::game::server_side::autosave_server::crate::game::ServerGame<'_>::on_tick_rate_changed"
kind = "HEAD"
cancellable = true
helper = "src/mixins/head.rs"
bindings = [{ name = "game", ty = "&mut crate::game::ServerGame<'_>", value = "&mut *self" }]
```

`src/mixins/head.rs`, the helper:

```rust,ignore
fn head(game: &mut crate::game::ServerGame<'_>) -> ::core::ops::ControlFlow<()> {
    if game.common.clock.rate() == 13.0 {
        return ::core::ops::ControlFlow::Break(());
    }
    ::core::ops::ControlFlow::Continue(())
}
```

`bindings` says what each helper parameter gets: here `game` gets `&mut *self`, the `ServerGame` the function was
called on. With `cancellable = true` the helper returns `ControlFlow<()>`: `Break(())` makes the function
return at once, and `Continue(())` lets it run. For a function that returns `R`, the helper returns `ControlFlow<R>`, and `Break(value)` returns `value`.

Run `cargo sunrise-mod build` from the mod project. The build log shows
`Function replacement: … without rebuilding the game` when it compiles the patch.

## Writing a helper

The helper file holds exactly one function: private, safe, with no attributes and no generic parameters
(except the `impl FnOnce` parameter of `WRAP_OPERATION`). The name is free, and the file has no `use` lines.

- It sees what the target's module sees: its items, imports and private fields (read the top of the target's
  file). That is why `crate::game::ServerGame` works in the helper and in `ty`. Write other names as full paths, such as
  `::core::ops::ControlFlow`. `crate::` is the target's gameplay crate.
- A field or method it can't see needs a [bridge](4-bridges.md). A local variable needs a `$local:NAME:N` binding.
- It calls your mod's crate by its Rust name: the package name with `-` turned into `_`. Don't declare helper
  files as modules in `src/lib.rs`. Shared code that needs private game items goes in a [support module](5-support-modules.md).

## Kinds

| `kind` | Your helper runs | It returns |
| --- | --- | --- |
| `HEAD` | at the start of the function | `()`, or `ControlFlow<()>` with `cancellable = true` |
| `RETURN` | on the value the function returns (`$value`) | the value to return |
| `OVERWRITE` | instead of the whole body; one mod per function. Needs `fingerprint`, the pin of the function it replaces: a line the game later adds to that function would otherwise vanish silently, so the build refuses a changed function (see `E_FINGERPRINT`) | the function's return type |
| `BEFORE_CALL`, `AFTER_CALL` | before or after one call in the body | `()` |
| `AFTER_ASSIGN` | after one statement that stores a call's result (`let x = f();`, `x = f();`) | `()` |
| `MODIFY_ARG`, `MODIFY_ARGS` | on one argument, or all arguments as a tuple, of one call | the new argument(s) |
| `MODIFY_CONSTANT` | on one literal in the body | the new value |
| `MODIFY_VARIABLE` | on one read or write of a local or parameter | the new value |
| `MODIFY_EXPRESSION_VALUE` | on the value of one call in the body (`$value`) | the new value |
| `WRAP_OPERATION` | around one call, which you get as `$operation` and may run or not. The receiver and arguments run at the call site, in order, before the wrapper. The wrapper's declared types are expected types for the game's own expressions, and the tool guards only part of that. Receiver: it must be a reference parameter of the target function (`engine.go`, declared as the parameter's own reference type); a computed receiver, such as a call result or a struct literal, is refused with `E_OPERATION_SIGNATURE` because its declared type can change which method the game calls. Binding the receiver to a local in the game's code does not make it a row. Arguments: one that carries a `?`, an `unsafe` block, a `const` block or a try block is refused with `E_UNSUPPORTED_CONTROL_FLOW` (`scale(default_value(0.1)?)` declared `f32` converts `0.1` through `f32`); a plain block elsewhere in the call is not refused. Not guarded: an ordinary argument, such as the literal in `width(1)`, takes the type its binding declares, and a named receiver's type is compared by its spelling, so declare exactly the game's types. See [what a mixin cannot target](#what-a-mixin-cannot-target) for alternatives | the call's type; a callee that declares no return type gives `()`, so `impl FnOnce(A)` and `impl FnOnce(A) -> ()` are the same operation |

The other kinds act on one place in the body, which a `selector` names as source text. For a call, write the
callee without arguments: `autosave_interval` or `self.next_autosave_interval`. A bare method name finds no method call: a method's selector writes its receiver as source text, `make()?.method`, and a count of 0 for a bare name called as a method here names that selector when it can be written. For
`MODIFY_EXPRESSION_VALUE`, write the whole expression: `autosave_interval(rate)`. `MODIFY_VARIABLE` uses
`variable` instead. `require` is how many matches the body has (inside `slice`, if set), and `ordinal` picks one, from 0.

For a struct-literal receiver, omit whitespace outside literals and the trailing field comma.
For example, given `ItemPlace::MenuSlot { menu, slot: n }.with_stack(host, |stack| stack.count())`,
use `selector = "ItemPlace::MenuSlot{menu,slot:n}.with_stack"` with `AFTER_CALL`.
If the helper reads the result, use `result = "Option<u32>"` here: `with_stack` returns
an option of the callback's result, not the stack view.

## Fields

| Field | Required | Meaning |
| --- | --- | --- |
| `id` | yes | The row's name, unique in the mod. Errors name it as `mod:id`. |
| `target` | yes | The game function's path ([Naming the target](#naming-the-target)). |
| `kind` | yes | One of the kinds above. |
| `helper` | yes | The helper's file, a `.rs` path under `src/`. |
| `bindings` | when the helper has parameters | One `{ name, ty, value }` per helper parameter, in order. `name` and `ty` repeat the parameter. `value` is a target parameter or its borrow (`self`, `&*self`, `&mut *self`, `rate`), or a tool value (below). |
| `cancellable` | no | `HEAD`, `BEFORE_CALL`, `AFTER_CALL`, `AFTER_ASSIGN`: the helper returns `ControlFlow` and can end the function. |
| `selector`, `require`, `ordinal` | one-place kinds | Which call, how many matches, which match. |
| `variable` | `MODIFY_VARIABLE` | `{ name, ordinal, at = "LOAD" or "STORE", parameter = true for a parameter }`. It replaces `selector`; `require` and `ordinal` then count accesses. |
| `priority` | no | Orders rows of several mods at one place: **higher** runs first. The default is 100. (Loop slots run the other way.) |
| `result` | `MODIFY_ARGS`, and `AFTER_CALL` reading the result | The selected call's result type. Refused on other kinds. |
| `fingerprint` | `OVERWRITE` (required), any other kind (optional) | A hash of the tokens of the target function's staged signature and body for the active build: any change to those tokens changes it, while ordinary comments and layout do not, outer attributes are not part of it, and a `cfg` that differs in the active build can change it. It therefore changes whenever the function changes in a new game build. A row whose target differs is refused with `E_FINGERPRINT`, which names the current value as `got`. On an `OVERWRITE` row, leave the pin out once and copy `got` from the refusal; on any other kind an omitted pin is not checked and nothing prints the hash, so a stale pin's refusal is where you read it. Never compute it from the original source text: the build stages a copy of the function. When the game changes the function, read the new function, check your replacement still suits it, then update the value. |
| `slice`, `argument` | no | `slice = { from = { selector, ordinal, require } }` narrows the search to a region; `argument` picks an argument. Both are in the tool's docs below. |

| Tool `value` | The helper gets |
| --- | --- |
| `$value` | The value being changed: the return value, the expression's value, or the argument, constant or variable. |
| `$arg0`, `$arg1`, … | An argument of the selected call (`WRAP_OPERATION`). |
| `$args` | All arguments of the selected call, as a tuple (`MODIFY_ARGS`). |
| `$receiver` | The receiver of a selected method call (`WRAP_OPERATION`); the first binding, and the operation's first parameter. It is a reference parameter of the target function, declared as that parameter's own reference type. A computed receiver is refused: see `WRAP_OPERATION`. |
| `$operation` | The selected call, as `impl FnOnce(args) -> result` (`WRAP_OPERATION`); the last binding. |
| `$local:NAME:N`, `$local_ref:NAME:N`, `$local_mut:NAME:N` | The `N`th local named `NAME` in the body, from 0: by value, `&` or `&mut`. |

horizon-mixins documents every kind and binding in full: [Mixin API](https://github.com/horizon-rust/horizon-mixins/blob/main/docs/mixin-api.md)
and [advanced injections](https://github.com/horizon-rust/horizon-mixins/blob/main/docs/advanced-injections.md).
Read these files at the `mixins` revision pinned in your manifest when checking tool-specific syntax.

## Naming the target

A target is the function's module path, then its type and name:

- a method: `sunrise_gameplay::game::server_side::autosave_server::crate::game::ServerGame<'_>::on_tick_rate_changed`, where the module is the one
  holding the `impl` block and the type is written as there, qualification and lifetimes included;
- a free function: `sunrise_gameplay::game::server_side::commands::misc::millis`;
- a trait method: the module of the `impl Trait for Type` block, then `<Type as Trait>` as written, then the
  function: `sunrise_gameplay_common::game::level_access::<GameLevel<'_> as LevelAccess>::block_state`.

Gameplay code lives in three crates:

- `sunrise_gameplay_common` (`crates/sunrise-gameplay-common/src/`): shared gameplay and `CommonGame<'_>`;
- `sunrise_gameplay` (`crates/sunrise-gameplay/src/`): server gameplay, `ServerGame<'_>`, and `server_side`;
- `sunrise_client_gameplay` (`crates/sunrise-client-gameplay/src/`): client gameplay, `ClientGame<'_>`, and `client_side`.

To get the module from a file, start from that crate's `src/` (its library name) and follow the `mod` items.
Each crate's `game.rs` (or `server_side.rs` / `client_side.rs`) declares each file of an **area**, a folder directly
under `src/game/` such as `world/`, with a `#[path]`, and an area is not a module.

So `crates/sunrise-gameplay/src/game/world/autosave_server.rs` is `sunrise_gameplay::game::server_side::autosave_server` (`world/` is an area).
By contrast, `crates/sunrise-gameplay/src/game/native_hooks/` is a module declared with `mod native_hooks;` in `game.rs`, so
`crates/sunrise-gameplay/src/game/native_hooks/base_server.rs` is `sunrise_gameplay::game::native_hooks::base`.
See [Repinning native targets for gameplay crates](../../how-to/native-mods/16-repinning-side-module-targets.md) for the canonical path rule and [Moving a native mod to the gameplay crates](../../how-to/native-mods/17-moving-to-the-gameplay-crates.md) for the step-by-step migration guide.

Any function in the `game` module of those three gameplay crates can take a mixin. A function in a crate below them, such as `sunrise_world`, needs
the marker `#[sunrise_mod_api_macros::replaceable]` in its source. Otherwise, target a replaceable caller or callee.

A method in a crate below the game crate is named by the module that **declares its type**, the path
`internals.txt` lists the type under, not by the module of the file that holds its `impl` block. A type is
declared in a module by its `struct`, `enum` or `union` item; a re-export (`pub use`) declares nothing.
`Behaviours::tick_precipitation`, whose `impl` is in `crates/sunrise-world/src/level/weather.rs` but whose type is
declared in `level`, is `sunrise_world::level::Behaviours::tick_precipitation`. So moving an `impl` between
the files of a crate keeps its targets. A target naming the `impl`'s file module instead is refused with
`E_MIXIN_TARGET_MISSING`, and the refusal names the right target.

A literal item-level `include!("path.rs")` adds declarations to the containing module, not to a new
module. A lower-crate copy and its mirror reach those declarations under the same visibility and
`cfg` rules as declarations written directly in that module. Each nested path is relative to the file
that spells it. An unreadable or invalid required fragment stops the build and names the file.
This does not make an `include!` inside a copied function body replaceable.

These functions are refused:

- generic over types or consts, or inside an `impl` block that is;
- taking `impl Trait`, returning `!`, or taking `self` by value;
- `const`, `async`, `unsafe` or `#[inline(always)]`;
- existing only under a `cfg` the signed build does not compile in (the function is then absent from the build);
- a body that declares a `static`, thread-local, `macro_rules!` or `impl`;
- a body that uses a location-dependent macro such as `file!`, `line!`, `module_path!`, `include!` or `env!`;
- a body that uses a non-exported crate-local macro defined outside its module path. Macros defined
  in the target module or its ancestors are copied with the function.

The one generic function you can target is a [published loop's body](3-loops.md#mixins-on-the-loop).

The tool plans against what the patch library compiles. The mod builder gives it the build's cfg set (the target's options and the features the prebuilt game was built with), and it drops the items, statements, fields, variants, parameters and match arms under an inactive `cfg` and expands `cfg_attr`. A function with an inner `#[cfg(test)] fn helper()` or a `#[cfg(feature = "x")]` statement takes its mixins like any other. The features are the game crate's: a `feature` predicate is decided only in the game crate's own functions. In a function of a crate below it (`sunrise_world`, say) it stays undecided, since that crate's resolved features are not the game's, and is refused. `unix`, `target_os` and the other options hold for every crate. The tool decides only what the signed build vouches for: `feature` in the game crate (from the game's feature list), `test` (the patch library is not a test build, so it is off), and the target facts that follow from the validated target (`target_os`, `target_family`, `unix`, `windows`, `target_arch`, `target_pointer_width`, `target_endian`, `target_env`, `target_vendor`, `target_abi`), read from the printed set and compared on their full values. Everything that depends on compiler flags (`debug_assertions`, `overflow_checks`, `panic`, `target_feature`, `relocation_model`, `sanitize*`, `doc`, `miri`) or on the original build's build script (any custom name) is undecided in both directions, listed or not. A `cfg` the set cannot decide (`version(..)`, `accessible(..)`, an expression-level attribute, a `feature` outside the game crate, a flag-dependent or custom name) is refused with `E_UNSUPPORTED_CFG`. This reduces the source inside a function the route already lets a row target; a function that carries a `cfg` or `cfg_attr` of its own is still not replaceable, active or not.

## Replacing the global fluid picker

The world generator's fluid picker (the sea and the lava below it) has two targets in `sunrise_world`:

- `sunrise_world::worldgen::aquifer::GlobalFluidPicker::compute`: the fluid level and state at one block position
  `[x, y, z]`;
- `sunrise_world::worldgen::aquifer::GlobalFluidPicker::level_bound`: the highest level `compute` returns for the
  block columns `min..=max` (`[x, z]`), or `None` when you cannot bound it.

**Replace the two together.** The terrain fill skips `compute` above the height `level_bound` gives, and writes air
there. A `compute` that raises the fluid in some columns, with the vanilla `level_bound` left in place, has its
fluid dropped above the sea: the water you asked for is missing from the chunk and from far terrain. Make
`level_bound` return at least the highest level your `compute` can return over the columns it is given. A higher
value is allowed and only costs a `compute` call per block; `None` makes every block ask `compute`. Neither
replacement is given coordinates beyond the columns of the chunk or tile being generated.

## What a mixin cannot target

| If the row is refused because… | Use this instead |
| --- | --- |
| The original game body uses a macro the tool cannot validate for a body hook. A macro in your helper, such as `println!`, `format!` or `log::info!`, is not subject to this check. | Use `HEAD` to leave the target body intact, or hook a call to that function. |
| The selector lands inside a closure, which can run separately from the target function. | Select a site outside the closure, or target a replaceable function that the closure calls. |
| `WRAP_OPERATION` would impose a type on a struct-literal receiver and could change method resolution. | Use `AFTER_CALL` to observe the call, or wrap a method on one of the target's reference parameters. |
| `RETURN` cannot cover an implicit exit through `?`, or the target result type is unresolved. | For `?`, use `HEAD` or hook the caller. If the result is plain `Self`, use the concrete impl type in your `$value` binding and helper signature; projections such as `Self::Output` are not resolved. |
| An import needed by the helper is not available in the copied scope. Lower-crate mirrors keep named imports used by the copies and helpers, not every sibling in a grouped `use`. | Name the item explicitly in the helper, or use its full path if it is accessible. A private item outside the copied scope may need a different target. |

## With other mods

Several mods' rows on one function all apply. An `OVERWRITE` must be the only mixin on its function,
from any mod including its own, and that includes a `HEAD` or a `WRAP_OPERATION` inside it. The tool plans every mod selected for a native build together, so a conflict between mods is found when they are built together, not when one package is checked, and not when an already built library loads.

## Errors

A row the build can't apply stops the build, naming the mod, the row and the reason. `<…>` is filled in.

| Code | Message | Fix |
| --- | --- | --- |
| `E_MIXIN_INVALID` | `<mod>:<row>: invalid target; name the game function's path` | Write the target. |
| | `… invalid helper; name a Rust file under src/ in this package` | Put the helper under `src/`, ending in `.rs`. |
| | `… invalid hook; a named hook is a mod_api::Hooks method; a mixin names its target` | Remove the row's `hook` (or `hook_version`) key and name a `target`, or implement the hook in `Hooks`. |
| | `… invalid target; a mixin targets a game function` | The target is in a mod you depend on. Call that mod's public functions instead. |
| `E_MIXIN_TARGET_MISSING` | ``<target>: no function `<path>` in this game build's function index (functions.json)``, or ``no crate `<crate>` in the game's source`` | Check the path against the source at your commit, module first. |
| | ``<target>: `<path>` names the module of the file its `impl` is in; a method below the game crate is named by the module that declares its type: `<right path>` `` | Use the path it names. |
| `E_MIXIN_TARGET_AMBIGUOUS` | `<target>: several functions have this path (a cfg-gated pair, for one)` | Target another function. |
| `E_MIXIN_NOT_REPLACEABLE` | `<target>: a function below the game crate takes a replacement only when it carries #[sunrise_mod_api_macros::replaceable]; …` | Target a game-crate function or a caller or callee carrying the marker. |
| | `<target>: <reason>`, such as ``it is generic over types or takes `impl Trait` …`` | Target a caller or callee that can be copied. |
| | ``<target>: it names `<path>`, which crosses a non-public `use` in `<module>` `` | The signature or body uses a re-export the prebuilt game keeps private. Target a caller or callee that can be copied. |
| | ``<target>: it names `<path>`, which reaches the non-public crate-root function `<name>` `` | The prebuilt game keeps that function private. Target a caller or callee that can be copied. |
| `E_MIXIN_SOURCE` | `<target>: <why>`, naming the unreadable, invalid or mismatched source file | Check that the SDK source is intact and matches the game build. |
| `E_MIXIN_INDEX` | `functions.json` or `loops.json` is missing, invalid, or describes a different build | Fetch the SDK for the build again. |
| `E_OVERWRITE_CONFLICT` | from the tool: `OVERWRITE must be exclusive on <function>; competing injections: <mod>/<row>, …`; it names every row, of any mods, on the function | For competing rows of one mod, remove one of those rows. For rows of different mods, keep only one of those mods installed. |
| `E_FINGERPRINT` | from the tool: `original function changed; expected <hash>, got <hash>`, or for an `OVERWRITE` with none: ``OVERWRITE requires the `fingerprint` of the function it replaces; expected <none>, got <hash>`` | Check the game's new function still suits your replacement, then set `fingerprint` to the `got` value. |
| `E_LOOP_ENTRY_REPLACED` | see [Published loops](3-loops.md#errors) | |
| `E_MIXINS_PATCH` | `tools/mixins/narrow-reference-rule.patch does not apply to horizon-mixins <commit>: <why>` | Not your mod: report it on the game. |

The tool's own codes, such as `E_MATCH_COUNT` and `E_UNSUPPORTED_SITE`, mean a selector, count or binding
does not fit the body; its docs list them. A helper with a wrong type is a compiler error under your mod's id.
