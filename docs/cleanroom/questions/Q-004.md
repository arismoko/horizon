# Q-004: may a pack rely on a loader ignoring a `shaders.properties` key it doesn't know?

- **Spec section:** revision 1, 0.4 (lines 51-56), "Out of scope": mod integrations (`dh*` programs and keys, Voxy
  `voxy.json`, Colorwheel `colorwheel.properties` and others); "Packs that ship such files must still load; the extra
  files are ignored". 3.2 (lines 463-465), "Keys seen in packs but not documented": `breaksAnisotropy` and the
  mod-support keys of 0.4, pointing to OQ-24 (line 1144): "`breaksAnisotropy` and other unknown keys: ignore with a
  log line?". 3.2 (lines 372-379) says an unknown flag in `iris.features.required` refuses the pack, and one in
  `iris.features.optional` is ignored.
- **Question:** is ignoring an unknown `shaders.properties` key a rule of the format in every tier, so that a pack may
  add a key that only some loaders read (an extension key such as `sunrise.hdr`) and still load unchanged elsewhere,
  or does 0.4's "must still load" cover only the mod-integration files and keys it lists, leaving other unknown keys
  undefined? If unknown keys are ignored, is a log line for each one part of the rule (OQ-24)?
- **What was observed:** `Properties::parse` keeps every `key=value` line of the active branches, whatever its key
  (`crates/sunrise-shaders/src/properties.rs:38-117`; keys are trimmed, and only `uniform.*`, `variable.*`, `image.*`
  and `size.buffer.*` lines have macros expanded). Its notes are for a line that is not `key=value`, an empty key
  included (`properties.rs:75-76`, `:110`); a repeated key, of which only the last counts (`:133-145`); an entry
  dropped because its expansion stopped (`:96-101`); and directive errors, a bad `#define` included (`:113-115`,
  `:156-178`). The game reads the file with the standard macros
  (`crates/sunrise-client-gameplay/src/game/interface/shader_packs.rs:424-429`,
  `crates/sunrise-shaders/src/options.rs:91-108`), built on `Macros::default()`
  (`crates/sunrise-shaders/src/macros.rs:53-55`, `:132-133`), that is `sunrise-glsl`'s default, which has no work
  budget and no argument-count check (`crates/sunrise-glsl/src/macros.rs:61-75`); so on this path the only expansion
  stop is a call nested too deep. None of these notes is about a key being unknown: a repeated unknown key gets the
  repeat note as any key does. Each consumer then looks up the names or prefixes it reads (`Properties::get` and
  `entry`, `properties.rs:119-125`; the loops over `entries` in `crates/sunrise-shaders/src/textures.rs:77`,
  `crates/sunrise-shaders/src/screens.rs:35`, `crates/sunrise-shaders/src/custom.rs:223`,
  `crates/sunrise-shaders/src/post.rs:886`, `:1955`, `:2006`, and
  `crates/sunrise-render-shaderpack/src/pack_atlas.rs:886-893`), so a key no consumer reads changes nothing. No
  `sunrise.hdr` key exists yet: sunrise-org/sunrise#5827 plans opt-in keys of Sunrise's own, `sunrise.hdr` and
  `sunrise.hdr.tonemap`, and needs a loader that doesn't know them to load the pack as if they were absent. Sunrise
  ignores unknown keys without a note for now.
